Abstract

Videos are 2D projections of a persistent 3D world, yet most tracking methods operate in pixel space, redundantly re-representing the same surfaces across frames. This limits them to either tracking a sparse set of query points or tracking densely but only over short clips. We introduce TrackEverything, a dense 3D point tracker that represents videos as persistent 3D scene tracks in world coordinates. Our approach combines three ideas: (1) tracking in 3D scene-content space, where repeated observations of the same surface are fused and occluded points persist without redundant representation; (2) a recurrent architecture that iteratively refines motion estimates and chains predictions across sliding windows for long-video inference; and (3) per-window static/dynamic classification that allocates trajectory decoding only to points in motion, saving computation on the majority of static scene content. At each window boundary, the 3D representation is voxelized to remove redundant points, ensuring that model complexity scales with the amount of distinct scene content rather than video length. To the best of our knowledge, TrackEverything is the first dense 3D point tracker that can track all points across all frames in long videos (1000+ frames). On TAPVid-3D, TrackEverything outperforms all open-source dense 3D trackers by over 20% APD on short clips and is the only dense method that scales to full-length sequences, where it remains competitive with state-of-the-art sparse 3D trackers despite tracking orders of magnitude more points.

Key Ideas

TrackEverything rests on three design decisions that together enable scalable, dense, long-video 3D tracking.

01

3D Scene-Content Space

Rather than tracking in pixel space — where the same surface is re-represented in every frame it appears — we lift features into world coordinates. Co-located points at a given timestep must correspond to the same surface, so a voxelized de-duplication at each window boundary collapses redundant observations. The representation grows only when the camera reveals genuinely new content, not with video length.

02

Recurrent Sliding-Window Architecture

A recurrent transformer iteratively refines each point's 3D position using 3D WAFT (Warp-Aligned Feature Transform) — a feature-warping technique that gives the model an implicit cross-correlation signal without expensive 4D correlation volumes. Predictions are chained across sliding windows of 16 frames, enabling seamless inference on arbitrarily long sequences.

03

Static / Dynamic Classification

At every window, each point is classified as static or dynamic. Static points — the majority in most scenes — need no further processing since their trajectories are trivially constant. Only dynamic points are passed to the trajectory decoder. This classification is re-evaluated each window, so a point can transition from static to dynamic as motion begins, allocating compute only where it is needed.

Method Overview

TrackEverything takes a video and 3D pointmaps (from depth sensors or an off-the-shelf estimator such as Pi3) and outputs dense 3D trajectories for all observed points. The pipeline is divided into four stages, run in sliding windows of L=16 frames.

§3.1 — Encoding

Each frame is encoded by a frozen DINOv3-small backbone + trainable DPT head, yielding a feature map that is lifted into a world-coordinate feature cloud via the 3D pointmap. Per-frame voxelization merges spatially co-located tokens to avoid erroneous cross-surface merges.

§3.2 — Iterative Refinement Transformer

A recurrent transformer with Nattn self-attention layers iteratively refines each point's 3D target position, visibility, and static/dynamic label. Before each pass, 3D WAFT samples image features at the current position estimate and birth location, providing an implicit cross-correlation signal.

§3.3 — Trajectory Decoder

Dynamic points are decoded into full L-frame trajectories via alternating within-track temporal self-attention and cross-attention from a [CLS] token to the feature cloud. Tracks are decoded independently, preventing distribution shift between training (random subset) and test (all tracks).

§3.4 — Sliding Window Inference

At each window boundary, the feature cloud is voxelized at the predicted target positions to merge spatially co-located points across frames — safe here because all points are at the same timestep. The deduplicated cloud is concatenated with newly observed points and fed into the next window.

Scaling Analysis

Peak GPU memory and latency as a function of video length and number of query points on PointOdyssey (single L40S-46G GPU). TrackEverything is the only method that tracks all points densely while staying under 30 GB at 900 frames.

Video Length Scaling

Any4D goes OOM at 96 frames. SpatialTracker-v2 at ~200 frames. CoTracker3 at ~600 frames. TrackEverything stays under 30 GB at 900+ frames.

Query Point Scaling

CoTracker3 latency surpasses ours at ~2,000 query points. SpatialTracker-v2 exceeds memory at 1,000 points. TrackEverything maintains near-constant latency up to 10,000 query points.

Why the Efficiency?

Three factors: (i) voxelized de-duplication of redundant 3D points, (ii) 3D WAFT in place of expensive 4D correlation volumes, (iii) sliding-window inference with O(scene content) complexity.

Limitations

TrackEverything demonstrates strong performance, but several limitations remain open for future work.

Model Scale & Data

Due to compute constraints, TrackEverything has not been scaled beyond 61M parameters nor trained on larger, more diverse datasets. Scaling both axes is likely to yield further gains, particularly on complex real-world scenes.

Unbounded Memory Growth

The current design retains all observed points indefinitely. Although voxelized de-duplication controls redundancy per window, memory will eventually become a bottleneck for very long videos (e.g., hours of footage). A dynamic eviction-and-retrieval strategy is needed for truly arbitrarily long sequences.

Reliance on External Geometry

TrackEverything relies on 3D pointmaps from an external estimator (e.g., Pi3) rather than predicting geometry end-to-end. While the architecture can in principle subsume geometry estimation, this direction requires substantially more training data and compute, which we leave to future work.
